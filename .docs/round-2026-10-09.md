## 1. Estate — the machine detail and Compare

### 1a. Findings coloured by severity (his 1; "yes")

The dossier's findings list dots critical red and high/medium amber, but the title is ink.
The card's ring is red for the same finding. **Build:** the finding title takes the severity
colour (`--est-red` for critical, `--est-amber` for high and medium, ink for low), so the
row reads like the card. CSS and one class on the title; the dot stays.

### 1b. Compare: aspects, differing rows only, a day selector (his 3, 4a)

"COMPARE of multiple machines has a Day selector where the user may select the day (NOT day
range) and it defaults to the most current." The API already takes `aspects` (os, hardware,
drives, dotnet, apps, sqlserver) and `asOf`; the panel passes every aspect and the estate's
global as-of. **Build:** in the Compare panel header, six aspect checkboxes (all on), a
*Differing rows only* checkbox (on — today's behaviour; off shows every row, identical ones
muted), and a *Day* select over the days every chosen machine has in common, defaulting to
the newest. The estate's global as-of seeds the select but the panel's choice is its own.
Changing any of them refetches. Labels and order as the Classic page had them.

### 1c. Software and Hosting at a chosen day (his 5)

The dossier fetches the snapshot at the machine's latest day. **Build:** a *Day observed*
select at the top of the dossier (the machine's collected days, newest first, default
newest); Software, Hosting and the facts re-render from that day's snapshot. Findings and
History are not per-day and keep their place. The URL carries it (`?machine=…&day=…`) so a
look can be shared.

### 1d. History: Comparison and List (his 2)

"it would be good to have a listing of overnights with changes, and expandable details.
History could have two tabs: Comparison (default) and List (week, month, all)." **Build:**
History gets two tabs. *Comparison* is today's From/To diff, unchanged. *List* is the
machine's collected days, newest first, **only the nights where the diff against the
previous collected day is non-empty**, each row a one-line count by section (*+2 apps, ~1
drive*), expanding to the full diff. A range segment *week | month | all* bounds the list.
One API call per expanded row (the existing machine diff); the list itself needs a
server-side summary per day pair — `GET /api/machines/{m}/changes?range=` returning
`[{ date, previous, counts: { section: { added, removed, changed } } }]`, computed with the
diff engine History already uses. Lean, decided: quiet nights are not listed, the range
header says *3 of 28 nights changed*.

## 2. Move It

### 2a. The board: PROD shows the current state (his 9, 10)

"Keep most recent shipped item per app in prod, this gives a sort of CURRENT STATE." Today a
release wholly at the top stage for more than `MoveIt:ShippedDays` folds out of the lanes
into the application cell (§27). **Build:** the most recently shipped item per application
stays in the top lane as a chip, *shipped 20 Aug*; only the older shipped ones fold. The
application cell's *Shipped: …* list keeps the older ones. Fixture pin: an app with three
shipped items shows one chip in PROD and two in the cell.

"when looking at the cards in the STAGE swimlanes, i want to know WHEN it arrived there."
The chip meta says *12 days here* or *12 days in VAL*. **Build:** the chip meta reads
*arrived 27 Sep · 12 days* (short date first, days after); the Coming lanes keep
*heard 3 Sep* wording. The release target, when there is one, is a second line on the
chip only when it is in the past or within seven days: *due 10 Oct* / *was due 3 Oct*.
Feature due dates are release targets; items carry none of their own.

### 2c. The release page: deployment history, adding and removing builds (his 13, 18, 19)

- **13:** "it would be good to see any history of deployments, in fact ALL deployments of
  each build/stage (with date)." *Builds it claims* lists where each build is now
  (release-builds.sql: `SupersededAt IS NULL`). **Build:** a second query,
  `board/release-build-history.sql`, every `moveit.Deployment` row for the release's builds
  plus asserted deployments from `ReleaseEvent`, ordered by build then stage then
  DetectedAt; the page shows it under each build as a collapsed *history (n)* line that
  expands to *DEV · WEB01 · 3 Sep → 12 Sep (superseded by 1.4.2)*, *VAL · 9 Sep → now*.
  A rollback reads as the same build appearing twice at a stage.
- **18:** "view builds not yet associated so they can be added." **Build:** under *Builds
  it claims*, a *Builds seen for this application, not claimed by any release* list
  (question 05's *attach a manifest* rows filtered to the app, plus DEV-only builds, which
  05 deliberately omits — here they are wanted), each with *Claim* which calls the existing
  build-upsert. Builds claimed by a different release are listed too, marked *claimed by
  Sprint 43*, with *Claim here* (a build can belong to two releases — the unique key is per
  release).
- **19:** "dis-associate builds … or to transfer to another Release." **Build:** *Release*
  beside each claimed build removes the `ReleaseBuild` row and writes a `ReleaseEvent`
  (kind `build-released`, the build in `Build`, the note *why*) so the act is on the
  record; *Move to…* is release + claim on the chosen release in one call. Work items whose
  `IncludedInBuild` is the released build stay as they are — the location rule then
  answers from whatever builds remain claimed, which is the honest consequence. The page
  says so in the confirm.
  **Open:** `build-released` is a new event kind; the lookups script carries it.

### 2e. Built, not seen that was at DEV (his 11)

"not sure how to assist, since you cannot see the data." He can — **built, step 6**:
`apptrak/sql/questions/14-why-not-seen.sql` — given a work item id, one result set showing
